# Fieldkit North Star Migration Plan

## Purpose

This document defines the target architecture for Fieldkit and a practical path to get there. The goal is not incremental cleanup; it is a paradigm pivot to a world-class, framework-agnostic form component system with predictable behavior and low cognitive load.

## North Star

Build Fieldkit as a Web Components library using Form-Associated Custom Elements, with React used only as an internal rendering engine where helpful.

### Why this paradigm

- Fieldkit enhances pre-existing HTML, forms, and native semantics.
- React root-level ownership conflicts with this requirement and creates bridge complexity.
- Form-associated custom elements give browser-native form integration, validation, and reset behavior without proxy inputs or DOM syncing hacks.

## Target Architectural Principles

1. One obvious module path per concern.
2. No compatibility shims in steady state.
3. No import-time side effects outside entrypoints.
4. Explicit, narrow error boundaries.
5. Prefer small, standard libraries over custom plumbing.

## Current Pain to Eliminate

- Dual-DOM bridge layer (native + React proxy) creates synchronization complexity.
- Recursive DOM scanners and mutation-driven orchestration duplicate browser primitives.
- Custom form reduction logic replaces built-in form behavior.
- Overlay positioning code manually tracks layout and scroll.

## Core Abstractions

### 1) FormFieldElement Base Class

Responsibilities:

- `static formAssociated = true`
- `attachInternals()` and form value propagation
- validity and custom error reporting
- lifecycle hooks (`connectedCallback`, `disconnectedCallback`, `attributeChangedCallback`)
- reset/state restore hooks (`formResetCallback`, `formStateRestoreCallback`)

Outcome:

- Shared form contract for all interactive fields.
- Removes ad-hoc event and value bridge logic.

### 2) Element Shell + UI Core Split

- `*Element` classes own browser contract and attributes.
- `*UI` React components are pure UI with explicit props/callbacks.

Outcome:

- Keeps React where it is strongest.
- Prevents browser contract logic from leaking into visual components.

### 3) Declarative Positioning

- Prefer CSS Anchor Positioning for dropdown/popover placement.
- Fallback to `@floating-ui/dom` only where anchors are insufficient.

Outcome:

- Deletes manual observer/scroll/resize plumbing.

### 4) Standard Form Data as Default

- Primary submission path: `new FormData(form)`.
- Optional post-processing utility for nested `data-tw-group` and `data-tw-array` semantics.

Outcome:

- Browser-native behavior first, custom shaping second.

## Phased Roadmap

### Phase 0: Stabilize Baseline (Short)

- Keep tests green and freeze feature surface.
- Add architecture decision records (ADRs) for paradigm pivot.
- Add high-level integration tests for form submission/reset behavior.

Exit criteria:

- Existing behavior is captured well enough to migrate safely.

### Phase 1: Introduce Foundation (Medium)

- Add `src/elements/FormFieldElement.ts`.
- Add custom element registry entrypoint in `src/index.ts`.
- Implement one low-risk element first (Multiline).

Exit criteria:

- One form-associated custom element running in production build.

### Phase 2: Migrate Simple Inputs (Medium)

- Migrate Pin and List to `PinInputElement` / `ListInputElement`.
- Keep current React UIs by mounting them inside shadow roots.
- Remove bridge-specific code only for migrated components.

Exit criteria:

- Pin and List work via element internals and native form submission.

### Phase 3: Migrate Complex Inputs (Large)

- Migrate Select and Signature.
- Replace grouping contexts with local element-owned registries.
- Move overlay/dropdown placement to anchors (or `@floating-ui/dom` if needed).

Exit criteria:

- Select and Signature no longer depend on bridge wrappers.

### Phase 4: Remove Bridge Layer (Large)

- Delete bridge wrappers, portal plumbing, and app-level mutation orchestration.
- Remove proxy input conventions and ignore flags used only for dual-DOM support.

Exit criteria:

- No remaining dependencies on old bridge architecture.

### Phase 5: Form Pipeline Simplification (Medium)

- Replace custom recursive form reduction as default path with `FormData`.
- Keep optional serializer utility for nested structures.

Exit criteria:

- Browser-native form behavior is default and documented.

### Phase 6: Hardening + Packaging (Medium)

- Ensure no import-time side effects except in entrypoint registration.
- Build explicit error boundaries per element type.
- Publish migration guide and compatibility notes.

Exit criteria:

- API stabilized, architecture simplified, docs updated.

## Deletion Targets (when phases complete)

- Any module whose only purpose is native/React value synchronization.
- Recursive scanners and mutation orchestration used to locate/upgrade nodes.
- Form reduction logic that duplicates browser submission behavior.
- Overlay systems that manually recompute layout each frame/event.

## Testing Strategy During Migration

- Keep unit tests for pure utils and UI behavior.
- Add element-level integration tests for:
  - form submit payload
  - required validation
  - reset behavior
  - attribute-to-prop updates
  - keyboard accessibility
- Keep Playwright flows focused on browser-native form semantics.

## Risks and Mitigations

- Risk: feature regressions during mixed architecture phase.
  - Mitigation: component-by-component migration and feature flags.
- Risk: custom element semantics unfamiliar to contributors.
  - Mitigation: base-class template, examples, lint rules, and review checklists.
- Risk: styling differences in shadow DOM.
  - Mitigation: CSS variable tokens and explicit `::part` API.

## Decision Log (Canonical)

- Paradigm pivot: React-app bridge -> Form-associated custom elements with optional React UI internals.
- Data flow pivot: custom submit reduction default -> native `FormData` default.
- Positioning pivot: JS-driven overlay tracking -> CSS anchors first, `@floating-ui/dom` fallback.

## Success Metrics

- 50%+ reduction in bridge/orchestration code.
- 0 proxy-field filtering in form pipeline.
- 0 import-time side effects outside entrypoint.
- New contributors can ship a small component change in under one day.
- Test runtime remains stable while integration confidence increases.
